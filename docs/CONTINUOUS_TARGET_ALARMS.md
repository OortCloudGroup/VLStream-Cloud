# 同一目标持续告警接入方案

状态：2026-09-30方案草案，待硬件确认原始报文与跟踪能力，尚未开发/部署新的持续告警合并接口。

## 已核验的现状

- 示例设备：`AETY-00-L8RV-81AA-00005000`，主动安全表已有583条事件。
- 当前以设备、messageId/eventId做消息幂等，不把独立事件ID按画面目标合并。
- 现有MQTT到主动安全DTO转换没有传递track_id、通道、跟踪会话和原始目标信息。
- 事件表data只有图片/位置/描述/媒体和消息事件标识，无法从历史记录可靠恢复同一人的目标身份。
- 协议有track_id说明，但文档不证明设备实际已实现。2026-09-30只读订阅40秒未收到新struct报文，未取得原始字段证据。
- 设备代码由硬件同事维护，平台不能直接修改设备跟踪/上报程序。

## 第一阶段：硬件侧减少持续异常重复首次上报

建议使用视频通道内稳定的目标跟踪ID，身份范围至少包含设备、通道、推理实例/算法、跟踪会话、track_id、事件类型。
track_id只表示同一段视频中的轨迹，不是跨镜头或长期的人物身份。不得只靠画面位置或“同类告警”识别同一人。

1. 目标异常达到连续确认条件后，创建一次告警生命周期，生成新eventId并上报首次告警。
2. 同一目标同类异常持续存在时，不再生成新的首次告警。首次消息重试保持相同eventId/messageId，沿用平台现有幂等回执。
3. 异常解除或目标消失达到结束条件后，结束设备端生命周期；再次异常生成新的eventId。
4. 设备重启、视频重连、推理实例重启或模型切换都更换trackingSessionId，防止track_id重复使用。
5. 多人同画面按各自轨迹独立告警。不同事件类型各自独立，不能全设备统一冷却导致另一人被漏报。

建议起始参数供硬件确认：连续异常确认2秒、目标消失/解除宽限10秒。参数需结合检测/跟踪帧率实测调整，
不是已经生效的配置。对于出现即需记录的事件类型，可关闭持续确认；不使用这些规则压掉紧急事件。

这一阶段能减少上报、图片上传与存储。平台现有事件处置状态不因设备异常结束自动变为“已完成”，人工处置状态与检测生命周期是两件事。

## 第二阶段：平台持续告警记录与证据更新

需要平台和设备协同升级，以下字段为新增提案，不能直接发送给当前旧服务并假定受支持。

| 字段 | 提案约定 |
| --- | --- |
| deviceId | 使用既有设备业务编号 |
| channelId | 实际视频源标识，一路输入也须有固定标识 |
| algorithmId | 字符串算法ID，保持现有语义 |
| inferenceInstanceId | 同算法多实例时区分运行实例 |
| trackingSessionId | 每次跟踪器重置生成新标识 |
| track_id | 稳定轨迹编号，允许0；缺失或无效标识不能作为可合并目标 |
| incidentId | 每次持续异常生命周期生成的UUID，START/UPDATE/END保持一致 |
| eventId | 每次上报的独立事件标识；重试相同消息保持不变 |
| eventPhase | START / UPDATE / END |
| sequence | 同一incidentId内递增序号，重试不递增 |
| observedAt | 实际观察时间，不使用收到消息时间替代观察时间 |

平台以租户、设备、通道、推理实例、trackingSessionId、track_id、事件类型隔离聚合，incidentId保持明确生命周期。
START创建一条持续告警，UPDATE更新最近观察时间、观察上报次数和有限证据，END记录结束原因/时间。
观察次数不是视频帧数；重试与乱序不增加次数、不回退时间。START重试不得重复创建；并发写入需唯一约束和事务保护。
证据使用首次图片、最近图片和有上限的代表性抓拍；图片上传频率与UPDATE频率分别配置，避免每次心跳都上传图片。

建议UPDATE起始间隔15秒，平台失联超时60秒（大于多次UPDATE周期）；静默失联只标记生命周期超时，
不把事件人工处置状态自动设为已完成。END不要求重新上传图片，平台必须先改造当前必填media校验。
有大模型复核的算法须明确复核START和必要升级证据，不能每个UPDATE重复启动复核；faceEvent保持原流程。
更新消息的消息幂等与生命周期合并必须分别持久化，不能复用旧findDuplicate(eventId)提前丢掉合法UPDATE。

缺少目标身份或旧设备继续按现有原始事件入库，标明不可聚合；不擅自退化为全设备时间窗口压制。
若使用第一阶段的稳定eventId重试方案，升级第二阶段时需协商明确协议版本，避免将合法更新误当重复消息。

## 硬件需要提供的材料

1. 一条当前真实aiBiz/struct原始JSON（Token、密码、签名URL去掉，可保留字段名和脱敏媒体元数据）。
2. 同一人在画面里持续异常的多条消息，证明track_id是否稳定；两个人同时出现的消息。
3. 通道、算法/实例、跟踪器会话来源；重启和短暂遮挡时轨迹编号如何变化。
4. 当前上报周期、解除/离开处理、帧级跟踪能力及可配置入口。

## 验收

- 同一人持续60秒只产生一个生命周期；另一个人出现独立产生一条。
- 同一人离开超过宽限再返回产生新生命周期；跟踪器重启且复用track_id不会合并旧事件。
- 同一目标不同事件类型分别记录；同算法多视频源不串事件。
- MQTT重试不重复计数，乱序UPDATE不倒退时间，服务重启/多实例仍正确。
- 缺track_id旧设备不会被静默丢弃；不影响faceEvent、人工处置和租户隔离。
- 设备断网标记失联状态，不能伪造正常解除；合并前后图片上传与存储数量有实测对照。

本方案未授权自动修并历史583条事件；历史图片不能单凭视觉相似可靠还原轨迹。
