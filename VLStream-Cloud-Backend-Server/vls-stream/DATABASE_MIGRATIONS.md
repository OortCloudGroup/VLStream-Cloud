# 数据库自动升级说明

VLStream Cloud 使用 Flyway 管理 v1.1.2 之后的数据库结构变化。后端每次启动时会先检查数据库，只执行尚未执行过的升级脚本，然后才启动业务服务。

## 开发时怎样新增 SQL

所有新的数据库升级脚本统一放在：

```text
VLStream-Cloud-Backend-Server/vls-stream/ruoyi-admin/src/main/resources/db/migration/
```

文件名格式：

```text
V主版本_次版本_修订版本_序号__英文说明.sql
```

例如，v1.1.3 的第一、第二个数据库改动：

```text
V1_1_3_001__add_device_status.sql
V1_1_3_002__create_device_group.sql
```

版本号必须递增，两个下划线不能省略。脚本提交并随新版后端发布后，使用者只需启动或升级容器，后端便会自动执行它。

## 必须遵守的规则

1. 已经提交或发布的迁移文件禁止改名、修改或删除；需要修正时新增一个更高版本的文件。
2. 一个文件只处理一组相关的数据库变化，文件名使用英文。
3. 删除表、删除字段、批量修改业务数据等危险操作，发布前必须备份并在数据库副本上验证。
4. 不要再把新的增量 SQL 放进 `vls-stream/db/` 后期待容器自动执行；该目录中的旧文件只作为历史或手工操作参考。
5. Flyway 默认开启。只有排查紧急问题时才可临时设置 `FLYWAY_ENABLED=false`，正常发布不能关闭。

## Flyway 记录了什么

Flyway 会在业务数据库中创建 `flyway_schema_history` 表。里面记录脚本版本、文件名、校验值、执行时间和执行结果。已经成功执行的版本不会重复执行；旧文件被人修改或升级失败时，后端会停止启动，避免程序在数据库结构不完整的情况下继续运行。

v1.1.2 是本项目接入 Flyway 的基线。已有数据库第一次使用新版后端时会登记这条基线，再执行 v1.1.2 之后的迁移；全新的 Compose 数据库仍先由发布包的完整初始化 SQL 建库，再由 Flyway 补充后续变化。

## 发布历史隔离

正式发布分支将当前开发迁移保存在 db/migration/mainline/，生产历史保存在 db/migration/release/。普通开发配置扫描 mainline；prod 配置只扫描 release，避免把尚未发布的开发迁移自动应用到生产数据库。

每个 release 目录都必须原样保留所有已经发布过的迁移，并仅追加本次正式发布的新增迁移。禁止修改、重命名或删除历史文件。当前 v1.2.11 在 v1.2.10 的历史后依序追加 V070 至 V073；主线开发文件保留在 mainline，测试读取该目录下的迁移。

## 算力实例默认可用与测试隔离修复

公共实例新记录默认 `public_state=FREE`、`workspace_dirty=0`，无需手工开启。持久状态用于跨进程保护占用、订单和工作目录，不应在每次启动时清空。

`1.2.0.073` 仅修复已由管理员确认接受残留目录的指定本地测试记录：同时匹配实例键、供应商实例、原 owner/claim、generation=1、已完成的指定训练任务，且没有活动付费运行、训练及启停检查操作时才解除隔离。已修复、新环境、其他实例或新占用均不变；不删除文件、订单或任务，也不产生费用。

升级已有业务库时备份后按正常 Flyway 启动迁移，不导入本地业务库快照，不使用全表 UPDATE 清除隔离。正式部署保持 Flyway 启用；若启动参数设置了 `spring.flyway.enabled=false`，此修复不会自动执行。其他隔离记录须核实各自来源，本迁移不会推断为测试数据。

## 角色菜单升级前检查

`1.2.0.069` 合并同时存在的原 RuoYi 系统目录（`1`、`100`–`104`）与 VLS 系统目录（`900000`、`900100`–`900500`）：保留 VLS 节点，将子菜单和角色绑定迁移到对应节点，再移除重复定义。只处理两端同时存在、权限码/类型/状态及父级符合预期的固定配对；身份或绑定租户冲突时停止。只有一套目录的环境保持原状。执行前备份 `sys_menu`、`sys_role_menu`、Flyway 历史，并在副本比较逐角色、逐租户的有效权限集合；保留节点的路径和授权不因合并被重置。该迁移不合并仅因共用权限码而存在的其他业务页面。

`1.2.0.062` 已在部分环境执行，其原脚本会调整默认普通角色及其菜单关联；后续 `1.2.0.068` 新增控制台基础菜单，并给已有有效角色补充先前默认开放的页面权限。该脚本最初以 `1.2.0.065` 编写，但从未在任何环境执行；为避免低于已应用最高版本的版本缺口，发布前已重编号为高于当前历史的 `068`。不能修改已执行的 `062`，也不能依赖 `068` 推断并恢复 `062` 可能删除的自定义授权。

升级尚未执行 `062` 的存量环境前，应在维护窗口停止角色和授权写入，备份 `sys_role`、`sys_role_menu`、`sys_menu` 和 `flyway_schema_history`，并先在数据库副本上按实际迁移顺序执行，逐角色核对原授权与结果。若需恢复自定义授权，只能依据可信备份、角色及租户归属逐项核实，不能按角色名称或猜测的租户批量补权。确认前不要让新后端自动执行该升级。

`068` 会在业务表写入前检查菜单 ID、权限码、父级及默认租户普通角色的状态；无租户的历史全局角色保持原状，不为其猜测或新增授权；默认角色缺失、停用、删除或重复时不会猜测管理员的意图。`068` 高于 `066`，会按正常版本顺序在 `066` 之后执行，不需要开启 Flyway 乱序。部署前仍应先只读检查这些条件并核对目标环境授权；已在隔离 MySQL 中验证该顺序，但不能跳过目标环境检查。若已触发迁移失败，Flyway 可能留下失败历史，须先核实真实数据库状态并按失败恢复流程操作；不要直接修改历史记录或强行跳过迁移。具体授权仍须在目标环境核验，菜单可见也不替代设备、数据归属和独立操作权限检查。

`067` 新建工作流可信归属和建单请求表，不会自动认定历史流程。启用相关权限代码前，须盘点仍需访问的历史实例，依据可靠证据和明确授权进行归属登记；单凭可编辑的旧工单关联不能证明归属。未能确认的实例按未知处理，严格模式会拒绝访问。目标环境的真实流程、调度及回滚仍须单独验证。
